## 0. 文档治理与当前决策

- 本文是 **V1.0 的唯一需求真源**；《完整项目规划与开发路线文档》只描述长期路线。两份文档出现冲突时，以本文为准。
- 架构、范围、数据留存和发布策略的变更必须写入 `docs/项目决策记录.md`，并在本文同步更新受影响的验收标准。

  - M0 只建设项目初始化与桌面端—Worker 启动链路；

  - 新建翻译列仅允许追加在数据区右侧；

  - 输出文件名主体和目录可修改，扩展名固定为 `.xlsx`，且不得覆盖原文件。

## 1. 项目背景

中俄贸易操作工作中，经常需要处理包含俄文内容的 Excel 文件，例如境外文件问题反馈、箱号异常、单证缺失、包装问题和运输异常等。

现有处理方式通常依赖人工逐行复制、翻译和回填，存在以下问题：

1. 逐行翻译耗时；
2. 原文、译文容易错行；
3. Excel 字体、字号、行高、列宽或边框容易被破坏；
4. 订单号、箱号、数字、型号等不可翻译内容可能被误改；
5. 常见物流术语缺乏统一译法；
6. 文件修改后难以追踪处理结果；
7. 文件可能包含敏感业务信息，不适合整体上传到云端。

第一版项目不建设完整外贸 ERP，而是提供一个本地运行、操作简单、可逐步扩展的文件处理工具。

## 2. 第一版目标

第一版只完成一个明确闭环：

```text
选择 Excel 文件
→ 识别工作表和主要列
→ 选择原文列与翻译列
→ 通过术语匹配或人工填写生成中文译文
→ 人工审核和修改
→ 写回 Excel 副本
→ 保持原文件结构与样式
→ 导出本地结果文件
```

在尚未启用在线翻译或本地翻译模型前，第一版不承诺对任意俄文句子进行自动翻译；它首先交付可审核、可安全回填的术语与人工翻译工作流。`Translator` 接口必须允许后续在不改动 Excel、审核和导出流程的前提下接入翻译引擎。

### 2.1 核心目标

- 支持 Windows 本地运行；
- 不需要部署服务器；
- 原始 Excel 文件只在本机读取和写入；
- 不直接覆盖原文件；
- 支持俄文问题反馈的中文译文回填；
- 翻译结果与原行严格对应；
- 尽量保留 Excel 原始样式；
- 支持人工审核、修改和重新翻译；
- 支持本地术语库；
- 支持任务失败重试；
- 为后续离线模型、批量文件和跨文件核对预留接口。

### 2.2 第一版成功标准

满足以下条件即可认为第一版具备内部使用价值：

1. 能正确打开常见 `.xlsx` 文件；
2. 能选择工作表、原文列和翻译列；
3. 能通过术语匹配或人工填写完成俄文到中文译文回填；
4. 箱号、数字、日期、订单号和型号不被误改；
5. 翻译结果不会串行或错行；
6. 原文件不会被覆盖；
7. 导出文件可正常用 Excel 打开；
8. 原有主要样式、行高和列宽基本保持；
9. 支持查看失败行并重新处理；
10. 无网络时仍可打开软件、读取文件、编辑译文和使用本地术语库。

## 3. 第一版范围

## 3.1 必须实现：P0

### 文件导入

- 支持选择本地 `.xlsx` 文件；
- 支持拖拽文件；
- 校验扩展名和文件是否可读取；
- 显示文件名、大小和本地路径；
- 默认以只读方式加载原文件；
- 自动创建处理副本或在导出时另存为新文件。

### 工作表和表头识别

- 读取所有工作表名称；
- 默认选择第一个可见工作表；
- 读取前若干行作为表头候选；
- 根据列名关键词推荐：
  - 箱号列；
  - 问题/反馈/异常列；
  - 翻译/中文翻译列；
- 用户必须能够手动修正推荐结果；
- 支持指定表头所在行。

### 翻译配置

- 原文语言：默认俄文；
- 目标语言：默认简体中文；
- 选择原文列；
- 选择目标翻译列；
- 翻译列不存在时允许新建；
- 支持“不覆盖已有译文”；
- 支持“仅处理空译文单元格”；
- 支持“跳过空值”；
- 支持“跳过纯数字、日期和编号”；
- 支持“优先应用本地术语库”。

### 翻译处理

- 按行生成唯一任务项；
- 每行保留：
  - 工作表；
  - Excel 行号；
  - 原文单元格坐标；
  - 译文单元格坐标；
  - 原文；
  - 译文；
  - 处理状态；
  - 错误信息；
- 批量翻译时必须保持输入与输出顺序；
- 翻译器返回结果必须携带稳定的行任务 ID；不得只依赖数组顺序关联输入和输出；
- 返回数量、行任务 ID 或保护片段校验不一致时，该批次必须标记失败，不得自动写回；
- 支持分批处理；
- 支持超时和失败重试；
- 支持中止任务；
- 支持最小任务恢复：每个批次完成后持久化行状态、译文和错误码；重启后仅重新处理未完成或失败行；
- “暂停”只保证在当前批次完成后生效；不得承诺取消已经发出的翻译请求；
- 翻译结果写入前先进入审核列表。

### 翻译保护规则

默认保护以下内容：

- 数字；
- 箱号；
- 订单号；
- 合同号；
- 运单号；
- 集装箱号；
- 日期；
- 金额；
- 货币代码；
- 产品型号；
- 文件编号；
- 邮箱；
- URL；
- 英文缩写；
- 单位符号。

处理方式：

1. 翻译前识别保护片段；
2. 使用占位符替换；
3. 翻译完成后恢复原值；
4. 对恢复结果进行完整性校验；
5. 校验失败时标记为“需人工确认”，不得静默写入。

### 审核与编辑

审核表格至少展示：

| 字段 | 说明 |
|---|---|
| 行号 | 原 Excel 行号 |
| 箱号 | 若存在箱号列则展示 |
| 原文 | 俄文问题反馈 |
| 译文 | 中文翻译，可编辑 |
| 状态 | 待处理、翻译中、成功、失败、已修改 |
| 操作 | 重试、忽略、恢复初始译文 |

支持：

- 单元格内编辑；
- 单行重译；
- 批量重译失败项；
- 搜索原文或译文；
- 只看失败项；
- 只看已修改项；
- 标记忽略；
- 撤销当前行人工修改。

### Excel 导出

- 默认生成新文件；
- 默认命名：

```text
原文件名_已翻译_YYYYMMDD_HHmm.xlsx
```

- 允许用户选择输出目录；
- 导出前检查目标文件是否存在；
- 已存在时要求更名或确认覆盖导出文件；
- 不覆盖原始输入文件；
- 翻译结果写入指定单元格；
- 新建翻译列时复制邻近列的基础样式；
- 导出后显示：
  - 输出路径；
  - 成功数；
  - 失败数；
  - 忽略数；
  - 总处理数；

为支持审核和恢复，任务行可在本地数据库中保存原文与译文；但操作日志不得记录完整原文、完整译文或请求体。用户清理任务记录或缓存时，必须明确展示删除范围，且不得删除用户的原始 Excel 文件。

## 4. 本地与离线策略

第一版定义为“本地桌面应用”，并区分三个层次：

### 4.1 完全本地能力

无网络时必须可用：

- 打开软件；
- 选择和解析 Excel；
- 预览内容；
- 手工填写或修改译文；
- 使用本地术语库；
- 使用历史翻译缓存；
- 写回和导出 Excel；
- 查看历史任务。

### 4.2 可选在线翻译

当前版本暂不启用在线翻译，也不在 M0—M1 实现在线适配器。后续若单独决策启用，在线模式只能发送需要翻译的文本，不上传完整 Excel 文件，并必须重新评审费用、数据外发范围和验收样本。

配置项：

- 翻译服务类型；
- API 地址；
- API Key；
- 模型名称；
- 单批数量；
- 超时时间；
- 重试次数。

安全要求：

- API Key 使用系统安全存储；
- 日志中不得输出完整 API Key；
- 不记录包含敏感内容的完整请求体；
- 明确提示在线模式会发送选定文本。

### 4.3 完全离线模型

第一版只预留接口，不要求正式集成大型本地模型。

可以预留统一接口：

```ts
interface Translator {
  id: string
  name: string
  mode: 'offline' | 'online' | 'glossary'
  translate(items: TranslationInput[]): Promise<TranslationOutput[]>
  healthCheck(): Promise<TranslatorHealth>
}
```

第一版至少实现：

- `GlossaryTranslator`：纯本地术语/缓存匹配；
- `ManualTranslator`：不自动翻译，仅供人工填写。

后续经独立决策再增加：

- `ApiTranslator`：可选在线翻译；
- `LocalModelTranslator`。

## 5. 用户流程

## 5.1 新建翻译任务

1. 用户打开应用；
2. 拖入或选择 `.xlsx` 文件；
3. 应用解析工作表和表头；
4. 应用推荐原文列和翻译列；
5. 用户确认工作表、表头行和列；
6. 用户选择术语匹配或人工填写模式；
7. 应用生成待处理行；
8. 用户点击“开始翻译”；
9. 应用显示实时进度；
10. 翻译完成后进入审核页面；
11. 用户修改异常译文；
12. 用户导出新文件；
13. 应用保存本地任务记录。

## 5.2 无网络处理

1. 打开本地 Excel；
2. 使用术语库和历史缓存匹配；
3. 未命中内容保持“待人工填写”；
4. 用户人工补充；
5. 导出文件。

## 5.3 失败恢复

1. 任务中断时保存已完成结果；
2. 再次打开应用后显示“未完成任务”；
3. 用户点击继续；
4. 已成功行不重复请求；
5. 仅处理未完成或失败行。

## 7. 技术架构

## 7.1 推荐技术栈

### 桌面端

- Electron；
- Vue 3；
- TypeScript；
- Vite；
- Element Plus；
- Pinia；
- Vue Router。

### 本地文件处理

推荐使用独立 Python Worker：

- Python；
- openpyxl；
- SQLite；
- PyInstaller。

### 本地数据库

- SQLite。

### 进程关系

```text
Electron Main
├─ 管理窗口和本地权限
├─ 调用系统文件选择器
├─ 管理 Python Worker
├─ 管理日志和配置
└─ 向 Renderer 暴露安全 IPC

Vue Renderer
├─ 页面和交互
├─ 任务状态展示
├─ 翻译审核
└─ 设置与术语库管理

Python Worker
├─ Excel 解析
├─ 单元格和样式读取
├─ 翻译任务预处理
├─ 保护片段处理
├─ Excel 写回
└─ SQLite 数据读写
```

第一版中 Python Worker 是 SQLite 的唯一读写方；Electron Main 和 Renderer 只能经受控 IPC 调用数据能力，不得直连数据库文件。这样可避免多进程并发写入、数据库锁和迁移责任不清的问题。

---

## 7.2 为什么使用独立 Worker

- 避免 UI 线程被大文件处理阻塞；
- 便于后续加入 OCR 和本地模型；
- Python 的 Excel 处理生态更合适；
- Worker 崩溃时不必关闭整个桌面应用；
- 可以独立编写测试；
- 便于后续替换实现。

## 7.3 进程通信

建议使用标准输入/输出的 JSON Lines 协议。

请求示例：

```json
{
  "protocolVersion": "1.0",
  "id": "req_001",
  "type": "request",
  "action": "parse_workbook",
  "payload": {
    "filePath": "D:/work/input.xlsx"
  }
}
```

进度示例：

```json
{
  "protocolVersion": "1.0",
  "id": "req_001",
  "type": "progress",
  "stage": "parse_rows",
  "current": 120,
  "total": 500
}
```

完成示例：

```json
{
  "protocolVersion": "1.0",
  "id": "req_001",
  "type": "completed",
  "data": {
    "sheetNames": ["Sheet1"],
    "rowCount": 500
  }
}
```

错误示例：

```json
{
  "protocolVersion": "1.0",
  "id": "req_001",
  "type": "error",
  "error": {
    "code": "WORKBOOK_OPEN_FAILED",
    "message": "无法读取 Excel 文件"
  }
}
```

要求：

- 每条消息占一行；
- 必须有协议版本、请求 ID 和消息类型；
- 错误必须有稳定错误码；
- 不允许在标准输出打印普通调试文本；
- 调试信息写入标准错误或日志文件；
- M0—V1 默认一个 Worker 同时只执行一个长任务；队列、取消、进度与恢复的精确定义以共享 schema 为准；
- 每个 action 的请求和响应 schema 必须位于 `packages/shared`，协议不兼容变更必须提升主版本号。

## 11. Excel 处理规则

## 11.1 读取规则

- 使用 `data_only=False` 保留公式；
- 不修改非目标工作表；
- 不修改非目标列；
- 原文单元格为空时跳过；
- 目标单元格已有内容且未允许覆盖时跳过；
- 合并区域内非左上角单元格不写入；
- 公式单元格默认禁止作为翻译目标列；
- 文件被其他程序占用时给出明确提示；
- 导入前必须检查加密、宏、外部连接、图表/绘图对象、数据验证、条件格式、数据透视表等高风险元素；检测到时须明确提示兼容性边界并允许用户取消，不得宣称完全无损。

## 11.2 新建翻译列

当翻译列不存在时：

1. 仅在数据区最右侧追加新列，不支持在中间插入列；
2. 写入列名；
3. 复制相邻列的基础样式；
4. 保留当前工作表冻结窗格；
5. 更新合并单元格引用时必须谨慎；
6. 第一版可优先选择“追加到数据区域右侧”，降低插列风险。

## 11.3 样式复制

必须使用样式对象复制，禁止直接共享可变样式引用。

复制内容：

- font；
- fill；
- border；
- alignment；
- number_format；
- protection。

译文单元格默认开启自动换行，并继承对应原文单元格的行高策略。

## 11.4 保存规则

- 先保存到临时文件；
- 保存成功后验证能否重新打开；
- 验证通过后再移动为最终输出文件；
- 保存失败时保留临时任务数据；
- 不得损坏原始文件；
- 临时文件应与最终文件位于同一卷；目标已存在时默认要求改名，不默认覆盖；
- 自动验证至少检查目标工作表、目标单元格、公式单元格和工作表可见状态；固定回归样本还必须使用 Microsoft Excel 人工或自动化打开验证。

## 12. 翻译质量规则

提示词或本地翻译规则必须要求：

1. 从俄文翻译为简体中文；
2. 站在中俄物流或贸易操作员角度表达；
3. 译文简洁、明确，适合填写问题反馈表；
4. 不扩写；
5. 不解释；
6. 不添加原文没有的信息；
7. 保留所有编号、箱号、日期、金额、型号；
8. 对单证名称使用统一术语；
9. 每条输入只返回一条对应译文；
10. 不返回序号、Markdown 或额外说明。

需要重点测试的歧义词：

- 文件；
- 单证；
- 发票；
- 装箱单；
- 标签；
- 标记；
- 唛头；
- 缺失；
- 破损；
- 不一致；
- 无法识别；
- 需补充；
- 需修改；
- 待确认。

## 14. 安全要求

### Electron 安全

- 禁用 `nodeIntegration`；
- 开启 `contextIsolation`；
- 通过 preload 暴露最小化 API；
- IPC 使用白名单；
- 禁止 renderer 直接访问任意本地路径；
- 禁止执行用户提供的命令；
- 文件路径必须规范化和校验；
- 不加载不可信远程页面。

### 本地数据

- API Key 使用系统安全凭据存储；
- 日志脱敏；
- 操作日志默认不记录完整原文；为任务恢复而保存的原文、译文和缓存仅存于本地任务数据库，并可由用户清理；
- 临时文件任务完成后可自动清理；
- 提供“清理历史和缓存”；
- 不收集遥测数据，除非用户明确启用；
- 提供隐私说明。

## 15. 性能目标

第一版建议目标：

- 10 MB 以内常见 Excel：可正常打开；
- 5,000 行以内单表：可完成预览和筛选；
- UI 在解析和翻译过程中保持可操作；
- 任务可以暂停或取消；
- 单行编辑即时响应；
- 大任务使用虚拟滚动；
- 任务状态每批更新，不逐字符刷新；
- 程序异常退出后尽可能恢复任务。

不应承诺固定翻译速度，因为速度取决于翻译方式、网络和电脑性能。

### 技术准备

- Windows 测试机；
- Git 仓库；
- Node.js 开发环境；
- Python 开发环境；
- 打包证书策略；
- 翻译服务测试配置；
- 错误日志目录；
- 自动化测试框架。

### 产品决策

已确认：

- 当前不启用在线翻译；无网络未命中内容保持“待人工填写”；
- 新建翻译列仅允许追加在数据区右侧；
- 最小翻译缓存和任务恢复纳入 V1；
- 用户修改后的译文只能手动加入术语库，不允许自动学习。

M1—M2 默认标准已确认：

- 任务和历史保留 90 天、精确翻译缓存 180 天、日志 30 天；
- 单个 `.xlsx` 不超过 10 MiB，单工作表有效区域不超过 5,000 行和 200 列；
- 高风险 Excel 只允许受限预览，M3 禁止导出且不提供强制绕过；
- 默认输出名为“原文件名_已翻译_YYYYMMDD_HHmm.xlsx”，文件名主体和目录可修改，扩展名固定。

延后决策：

- 自动翻译能力的引入时点、技术选型、费用、凭据管理与数据外发边界；未经单独确认不得接入。

## 22. 第一版最终定义

第一版不是通用文件 AI 平台，而是：

> 一款 Windows 本地运行的中俄贸易 Excel 翻译工具，重点保证俄文问题反馈到中文的准确回填、人工审核、术语统一和原文件格式稳定。

任何新增需求都应先判断是否影响这一核心闭环。若会显著增加文档类型、业务对象或部署复杂度，应进入后续版本规划，不直接并入第一版。
